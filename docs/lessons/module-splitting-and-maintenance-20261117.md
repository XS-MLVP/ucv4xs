# 模块切分与跨基线维护复盘（2026-11-17）

## 问题与结论

本轮从验证包拆分、DUT 工作入口，推进到以模块为主对象的树形管理草案。用户提出两个核心要求：
按模块管理验证现状，责任分工用于维护；模块随设计变化后仍应可追踪。

**模块树适合组织当前工作，长期维护还需要持久模块身份、版本绑定和增量变更处置。**
当前草案完成了静态映射，尚未提供跨基线增量同步。可执行方法收敛到
[模块身份与生命周期维护（待审核）](../../skills/pending/module-identity-and-lifecycle.md)，
由[项目工作流](../../skills/ucv4xs-workflow/SKILL.md)导航；本文保留本次案例与限制。

## 2. 切分过程中的主要经验

| 原先容易采用的假设 | 本次反例 | 修正依据与维护方式 |
|---|---|---|
| 代码包边界可以直接作为模块树 | ITLB 在 Frontend，FrontendBridge 在 MemBlock；AIA 部件分布在总线侧和 CSR | 设计模块树与代码包分别映射；包保持维护/执行职责 |
| 按固定 RTL 层级切分即可均衡工作 | BPU 已到子预测器，整数算术还包在 ExuBlock，浮点/向量包在 IssuePipe 内 | 按真实模块逐层评审；状态机、算法、接口及维护收益决定深入程度 |
| 已登记 DUT 较多就说明对象齐全 | L2 有较多通道/缓冲切点，仍需补审 MainPipe 与 MSHR；LLC 同样有主流水和目录缺口 | 同时从设计结构和既有合同反查关键模块，不把资产数量当完整性 |
| 每个生成名都需要独立管理建设 | 16 个 UncacheEntry 已共用一个 testbench | 可以形成模块族记录，但保留各 DUT 的配置、选择和结果 |
| 同名或同源即可共用全部结论 | 三处 MainPipe 的来源不同；MSHRBuffer 的 refill/release 角色不同；ITLB 与 DTLB 角色不同 | 名称/定义位置用于候选归并，角色、接口和合法域仍需评审 |
| 子模块通过就能完成父模块 | Bpu 仍有选择、历史、训练和恢复组合；Region 仍有发射到写回的身份传播 | 父模块保留自身记录与合同；子级状态不自动汇总为父级验收 |
| 把全局模块图强制变成唯一物理树 | FreeList、寄存器/仲裁、通用缓冲存在多处使用 | 树表达主要归属，保存实际多父实例；间接边和复用边不能伪装为直接包含 |
| 每次重新生成清单即可维护 | 路径派生 ID 会随源码移动改变；扫描新配方不能保留已撤下对象 | 采用后持久保存 ID；比较旧记录与新观察并集，先形成变化提案 |

已有的需求、功能点、合同和测试不能被树形记录替代。模块树帮助查找“验证谁、做到哪里、缺什么”，
具体正确性和完成条件仍在所属规格；维护负责人可变化而不改变模块身份。

- 当前 `Ftq.scala` 存在 commitPtr、提交元数据和向 BPU 提交的逻辑。这个观察支持审查 Ftq 的承接范围，
  **不证明旧 CQ 的容量、多 lane 保序及其他条款均原样保留或已经验证**。
- 原 `ftq/commit_queue` 配方、合同和实现仍保留；草案历史记录 ID 为 `M-db19f556e6e1`，资料入口存在。

依据：[FTQ 设计与基线边界](../../suites/frontend/ftq/docs/spec/design/README.md)、
[FTQ 功能点](../../suites/frontend/ftq/docs/spec/design/functional-points.md)。
正确后续是逐条确认旧要求保留、改变、承接或有依据取消，再记录新基线处置；不能把旧模块行删除当成完成。

### TLBNonBlock：旧技术切点消失，新变体不自动承接旧合同

- 当前源码与完整生成中无 TLBNonBlock；本次源码查询也未发现该类定义。
- 当前 MemBlock 的 load/store/prefetch 分别使用 TLB 的三个生成变体，旧 `mmu/tlb` 对应 Frontend ITLB。
- 这些新位置是已核对事实，但旧 tlbn 的多端口合法域、时序与取消语义需要单独映射。
- 原 `mmu/tlbn` 配方、资料和实现仍保留；草案历史记录 ID 为 `M-eeb716740ed3`，资料入口存在。

依据：[MMU 当前绑定与历史接口边界](../../suites/memblock/mmu/docs/spec/design/README.md)。
不能直接将旧 tlbn 改名为某个 DTLB，也不能把旧结果复制到三个新变体。

这两个案例说明的是当前独立 top 的变化，**没有证明验证资产在本轮整理中丢失**。
如果今后从活动配方撤下旧切点，模块历史记录仍须保留；当前草案生成器尚不保证这种跨次延续。

## 4. 当前草案的可维护性限制

静态检查通过与长期更新可靠是不同结论。对本次生成脚本的复核发现：

1. **ID 只在本次草案内稳定。** `stable_id(namespace, source, name)` 由路径和名称派生。
   模拟把 TAGE 来源从现路径改为 `synthetic-moved/Tage.scala`，ID 从 `M-d5501b83d3df`
   变为 `M-d580265f1fec`。这是合成敏感性探针，不是设计实际发生变化。
   首次生成方式可以作为分配候选，采用后必须保存 ID 并读取旧映射，不能跨版本重算。
2. **输入是一个已冻结快照。** 脚本核对前次输入哈希，输出使用排他新建；它没有基线差异匹配、
   退役记录继承或线上 recordId 对账逻辑。因此不是持续同步命令。
3. **归并属于启发式候选。** 同源位置和规范化名字可以帮助发现参数族，仍未证明接口等价或 testbench 可复用。
4. **最近共同上级可能变化。** 新增使用位置就可能改变推导出的归属；实际维护应审查这个变化，保留 ID 和人员信息。
5. **初始状态不是人工进度。** 草案从骨架/旧资产观察初始化，负责人为空。用于后续更新时，不能覆盖已维护字段。
6. **管理清单尚未穷尽。** 草案选定族涉及 487 种生成类型，完整生成有 2,024 种；剩余对象要按管理价值评审，
   不因未入树就认定不用验证，也不要求全部变为独立人员任务。

当前公共工具 `ucv.documents.binding_observation` 已能区分旧基线观察、top 不符、top 缺失、骨架与待复验，
`ucv info/check/docs` 提供导航与结构检查；它们尚未实现模块 ID 的跨基线匹配、继承与增量同步。

## 5. 长期维护应当怎样收敛

- **模块主记录延续。** ID 与历史保持；名称、父级和本版绑定有证据地更新。
- **按差异维护。** 每次升级先得到新增、改名/移动、接口/配置变化、拆分/合并、内联、缺失待核实等提案，
  只审查受影响项；历史对象继续可查。
- **按基线判定。** 旧 PASS/FAIL 保留原范围，新版标待评审/适配/复验；生命周期处置不等于功能通过。
- **物理变化不强制搬目录。** 管理归属和技术绑定变化先落到模块资料；有实际维护或运行收益时才迁移实现。
- **Skill 固化判断方法，工具保证机械一致性。** 语义承接需要设计证据；唯一映射、无环、哈希和字段保留由确定性检查保证。

新增的方法仍标为待审核；真实跨基线增量同步、持久身份存储与外部表差异更新尚未实现或验证。
本轮整理经验没有批准候选 DUT，也没有更改硬件验收结论。

## 既有参数族的 per-DUT 迁移补充（2026-11-17）

用户随后要求将已经共用的实现也拆开。6 组旧包涉及 29 DUT，迁移后全仓从
313 增至 336 个独立 testbench；DUT 与模块身份数量保持。关键经验：

- 目录拆开还不足以保证选跑独立。LSQ fixture 原先枚举同族全部变体，须固定到所属 DUT；
  MMU 的混合文件与 shared 自检须按实际检查语句拆分，保留原激励、预期及标记。
- VAGQ 单 DUT 启动原先会读取其他 DUT 元数据，并核验全套 RTL；延迟 fixture 导入、按实际
  加载对象核验收据后，独立入口可用。联合场景仍明确核验全部参与对象。隔离控制必须同时证明
  “不读取未选对象”和“所选对象缺失/错误时仍拒绝”，不能靠取消身份检查取得成功。
- 原模型供父级使用的真实复用按职责转到 shared；单 DUT 保留完整自身实现，避免以导入另一个
  DUT 的薄壳充当独立包。公共指针类的提取保留 AST 与既有 API。
- 旧文件可能有多个实现后继，旧测试节点则应尽量精确映射。路径导航增加多后继列表，唯一入口
  API 对歧义报错；MMU 从测试中提取的 model/checker 属于部分源码承接，不冒充整份测试文件。
- 根工具自检的子进程也需明确临时 pytest 根；仓库内 basetemp 曾使报告落在仓库 results，
  出现 424 PASS / 2 FAIL。修正临时根后同场景 2 PASS，全量 426 PASS，副产物有归档处置记录。

三工程 3,522 个原节点全部保留承接，新增净 51 项只来自自检拆分及启动/checker 控制。
