# 维护文档与工程规格

本指南用于选择写入位置、更新现有正文并完成检查；不要求调整验证语义或重跑硬件。
开始前先查[使用文档入口](../README.md)和现有同主题内容，避免再建一套重复说明。

## 先选择文档类型

仓库使用 [Diátaxis](https://diataxis.fr/) 区分读者需求，而不是按目录名称凑四份文档：

| 读者现在需要什么 | 文档类型 / 本仓库落位 | 应包含 | 不应混入 |
|---|---|---|---|
| 跟着练习、获得第一次成功经验 | 教程，`docs/tutorials/` | 固定示例、前置条件、逐步操作、每步可观察结果和有限完成目标 | 多方案决策树、修改规格任务、完整参数表 |
| 完成一个已经明确的任务 | 操作指南，`docs/how-to/` 或已有专题路径 | 条件、可替换参数、必要步骤、核验方法、失败分支 | 从零教学、长篇设计背景 |
| 查准确的参数、字段或位置 | 参考，`docs/reference/` | 与当前 CLI/配置对应的事实、默认值、约束和输出结构 | 未执行的成功承诺、逐轮进度 |
| 理解为什么这样设计或如何解释结果 | 解释，现有 `architecture.md`、`baselines.md`、`maintenance.md` | 概念、关系、取舍、边界及相关操作链接 | 作为唯一来源的复制命令流程 |

既有稳定专题路径可以保留，由入口按类型导航；Diátaxis 不要求为排版搬迁历史文件。
设计/验证规格、Bug、状态页与复盘是另一类工程资产，不强行改造成教程。

## 更新一篇使用文档

1. 写清读者要完成的任务或要查询的事实，找到已有权威页面；同主题原位更新。
2. 命令参数从 `./scripts/ucv <command> --help` 与 `src/ucv/` 核对，路径从 `ucv info`
   和配方核对，不从历史运行命令推导当前接口。
3. 教程使用真实可定位的单一 DUT/nodeid；通用指南用明确声明的占位符。说明命令的 cwd、
   前置环境、是否下载/生成/写文件、结果目录必须新建等限制。
4. 每步区分“应看到的输出”与“已经实测的结果”；只校验了 Help/配置时，不写成已重跑硬件。
   运行中不要编辑参与源码身份的工程 Markdown。
5. 新页登记到对应根的 `docs/navigation.json`，并在入口按教程/指南/参考/解释连接。
   移动旧页时另保留位置映射和原证据，不用当前页面覆盖旧哈希。
6. 核对相对文件链接、标题锚点、示例 nodeid 与配置，再执行 `./scripts/ucv check full`
   和 `git diff --check`。`check` 校验文件链接，不验证标题锚点或命令语义，后两者需要另行检查。
7. 只有文档变更时不默认构建/仿真；涉及公共代码或 DUT 语义变更时，按实际范围另跑测试。

只更新根使用文档不需要执行 `ucv docs full --write`。该命令刷新工程生成区块，不负责
编写教程、CLI 参考或当前硬件结论。不要覆盖本地已有未提交内容，历史报告和来源清单保持原义。

## 工程目录与 README 的职责

各工程的集中资料使用同一布局，DUT/实现关联、配置和基线从工程配方与 workspace 解析：

```text
docs/
├── README.md                    # 当前范围、规格和问题入口
├── spec/
│   ├── design/                  # 职责、接口、时序与行为要求
│   └── verification/            # 场景、独立预期、观察、覆盖与完成条件
└── bugs/
    ├── README.md                # 从问题记录生成的当前汇总
    ├── open/                    # 仍需处理、待定位或待复验
    └── closed/                  # 有处置依据的完整问题档案
```

工程 README 简述工程与运行入口，`docs/README.md` 汇总资料，`bugs/README.md` 汇总问题。
详细要求放规格，详细问题分析放对应 Bug，运行明细留在结果存储。小工程可先用两个
`spec/*/README.md` 承载正文，需要时再按 DUT 展开。

DUT 的 `testbenches/<testbench>/README.md` 是 schema2 的工作入口：链接具体规格、公开 API、测试、
最小命令和正式问题记录，正文仍由上述权威位置维护。内容要求及单文件/子包选择见
[testbench 目录规范](../reference/module-layout.md)，旧工程适用其中的 schema 兼容规则。
已有共享包的 `testbenches/shared/README.md` 独立链接实际职责、工程合同和共享自检，
由同一工具生成；它不承载 DUT top 或独立原生库身份。新增当前入口同样登记到工程
`docs/navigation.json`。`ucv docs --write` 生成各 README 区块，工作入口自动参与
`ucv check`；生成区块之外可写人工说明，问题状态与运行计数通过工具查看，避免重复维护。

## 权威来源与更新方式

| 内容 | 权威位置 | 更新方式 |
|---|---|---|
| 使用教程、操作方法、参考、解释 | 根 docs 的相应入口 | 同主题原位更新；使用 Diátaxis |
| 设计要求、接口与时序 | 工程 docs/spec/design | 按设计工程结构，设计/验证共同 review |
| 验证场景、判定依据和完成条件 | 工程 docs/spec/verification、既有功能点文档与合同 | 稳定 ID、维护关联；按验证工程结构 |
| DUT/testbench/源码/环境资源地图 | 配方 + workspace.json | `ucv info` 生成 |
| 实际执行状态、计数和覆盖 | 运行收据与产物 | `ucv report` 生成到结果目录 |
| 问题及处置 | docs/bugs/open 或 closed 中的单一记录 | 编号不变，保留各基线结论和证据 |
| 重要设计决定 | 对应规格的依据章节 | 记录决定、适用版本、review 与原依据 |
| 临时探索和逐步操作日志 | 本地结果目录、任务或 PR | 提炼长期结论后更新所属正文 |

工程根的 `verification_plan.json` 已删除。现行说明直接链接既有规格、功能点、合同和
问题记录，不建立改名替代计划文件，也不要求运行前另填残余 JSON 清单。历史报告、
日期记录和哈希清单中的旧路径/命令保持原字节；在当前入口说明其历史用途即可。

## 日常修改

1. 从工程 README、docs/spec 和 `ucv info <suite>` 找到所属主题。
2. 修改已有正文与对应配置；新独立主题才新增文件。
3. 新增当前使用页面时，登记到该根的 `docs/navigation.json`。
4. 修改问题记录或 DUT/shared 入口后执行 `ucv docs <suite> --write`，刷新问题汇总与各 README
   的生成区块。
5. 执行 `ucv check <suite>`，运行与实际变更相关的检查。
6. PR 描述记录本次修改摘要，Git 保存修改历史。运行结果链接到对应证据。

人和 AI 使用相同流程。路径解析、目录创建、release 获取、关联检查和结果统计由 `ucv`
承担；工程师负责行为定义、独立预期、语义 review 与缺陷归因。

## 问题生命周期与版本一致性

每个问题只维护一份 Markdown，使用稳定 ID；结构化字段与正文放在同一文件，格式见
[工作空间参考](../reference/workspace.md#问题记录)。目录决定当前状态，文件内不重复填当前 status。

- 发现或调查中放 `open/`。修复待验证、升级后未复验也留在此处。
- 有证据处置后移到 `closed/`，记录原因：修复已验证、原问题不成立、重复、设计退役。
- 再次出现时沿用编号移回 `open/`，记录重开依据。移动同时更新引用和生成索引。
- 各版本分别记录 `open / closed / unverified`；历史 FAIL 和后续根因更正均保留。
- 当前目录表示当前主线的处理状态。某基线修复不自动意味着其他基线也已修复。

已撤回的历史误报可以继续保留在 `closed/`，同时把新基线标为 `unverified`；关闭的是
原指控，并不证明新版本同域行为通过。纯范围约束、资源策略和已接受限制维护在规格的
范围/残余章节；`retired` 只用于有证据的设计或接口退役。

归因复核同时更新 `kind` 与正文。初始化、协议激励或采样错误的修正应记录为验证侧原因；
撤回原 RTL 指控使用 `invalid` 并引用裁决证据，不能仅凭后续 PASS 写成 RTL 已修复。
保留的旧 `known-issues` 等清单应在文件自身注明历史日期、基线和用途，并链接当前问题记录。

既有功能点、合同与验证规格继续维护功能要求、实现关联与验收缺口；涉及具体问题时引用 Bug ID。
问题的当前处置只维护在问题记录中。缺口的验收关闭还需覆盖或集成证据，不能因关联的
单个 Bug 关闭而自动关闭整个验证范围。

修复验证须绑定原反例与合法对照、实际设计基线/RTL、验证代码与合同、选择范围和种子。
同 nodeid 的预期或激励发生变化时记录依据；用例重命名/拆分保留旧新关联。未选择、SKIP、
XFAIL、证据缺失都不能作为已解决证据。无问题登记只说明尚无记录。

正式迭代通过仓库 commit/tag 固定规格、问题和验证代码。`ucv run` 在运行开始快照问题
记录，`ucv report --compare` 比较稳定 ID 的新增、移除、关闭、重开及记录变化，并另列
基线与用例差分；这些差分供 review，不自动认证修复。旧运行没有问题快照时标记不可比较。
工程 Markdown 与机器合同参与源码身份校验，运行期间修改会导致完整性错误。

新运行按冻结的问题快照判定：位于 `open/`、在当前基线仍开放或未复验的问题会使纯
PASS 汇总为 `INCOMPLETE`，实际 case 计数保留，真实 FAIL/ERROR 优先。功能标记统计
使用 `scope=collected-test-markers`，只覆盖实际收集标签。问题阻塞规则只用于显式带
`acceptance_source='issue-records'` 的新运行；无此标志的历史运行维持原解释，含
`residuals` 时按冻结旧字段读取，不能拿当前问题状态或删除计划后的口径重标历史结论。

问题索引按该次 Git 快照的 open/closed 目录生成，运行快照只代表执行开始时的已登记状态。
关键运行证据应按仓库资产规则保存可访问位置及哈希；Git 不保存被忽略目录里的日志内容。

## 整理已经累积的材料

先用 `ucv check <suite> --json` 查看当前页面和未索引清单。按主题逐项处理：

- 持续有效的规则合并到当前规格或指南；缺陷分析合并到对应问题记录。
- 当前计划维护范围、实施顺序和完成条件；逐轮进度归入所属主题证据，并在页面自身标注
  日期与基线。进入当前页面后，应能直接分辨持续有效条款与历史执行结果。
- 一次实验的事实保留原基线、选择范围与证据。已有独立价值的历史材料可放所属主题的
  `evidence/`，通过规格或 Bug 引用，保留一份。
- 重复正文在完整提炼、确认引用与未提交内容已保全后移除；用 Git 追溯其版本。
- 迁移前检查代码、机器账本、相对链接与动态拼接路径，机器消费的合同一起迁移引用。
  当前指南只更新实际已迁移工程的命令示例；局部迁移不写成全仓完成。冻结历史脚本、
  日期报告和哈希清单保留原字节，旧路径通过现行入口或映射说明。
- 冻结收据保留当时的路径、哈希和命令；需要从旧路径寻找当前文档时，在所属根的
  `docs/navigation.json` 的 `relocations` 中记录位置映射。当前文档经修订后不是原字节快照。
- 外部产物不可用时如实标记。历史非 PASS 结论保持原义。

当前状态页维护当前快照。工程不新建通用 `history/` 或按版本复制全部规格/问题目录。
已有仓库级来源/哈希索引继续服务原证据接入；问题目录、Git 与运行存储分别承担问题档案、
版本历史和实验事实。规格和 Bug 使用稳定文件名。

`docs/status.md` 只保留当前范围、最近一次验收摘要和未完成项；不要持续追加逐轮进度、
旧目标状态或复制各工程报告。清理重复正文前核对原始证据入口，未提交的独有内容先保留
原文与哈希。教程和当前工作入口链接当前状态；带日期的旧交接记录只用于历史追溯。

## 发布为 Web

网站从同一份 Markdown、工程规格和工具生成视图构建，维护一份内容源。首版通过 GitHub
即可阅读与 review；本轮的本地检查不要求部署网站或接入 CI。
