# 如何制定退出标准并处置残余

## 何时使用、准备什么

开工时制定验收合同，交付时逐项核验；不是在全绿后倒推标准。输入是责任/等价类矩阵、需求追溯、当前结果、检查器自检和已知缺陷。

## 怎么做

1. **事先定义退出范围。** 写清 DUT/参数/版本、必验功能、允许的范围排除及交付要求；“文档整理完成”“测试执行完成”“功能验证通过”分别判定。
2. **逐项对账。** 每个功能点标已动态检查、不适用（附依据）或残余；reached、checked、独立 oracle、完成性和正负对照分别核实。填满表不等于语义闭合。
3. **将覆盖缺口反馈到需求。** 对 line/toggle/branch 的未覆盖项定位：已有功能点缺枚举，还是整类行为未定义，或当前配置/观察点限制。补需求/用例并重跑相关 DUT；不能只追数字。
4. **给残余排责。** 每项写原因、影响、证据、责任层级/承接方、下一实验与阻塞性；“缺 selector”“暂未命中”不能独自证明不可达。内部宽于端口、字段被裁剪的项按 [观察点精度](observation-precision.md) 保留，关闭理由不能是“端口就这么多位”。
5. **区分“倾向保留”和“已经通过”。** 筛选阶段未证明正确性就留下；关闭阶段没有消费者合同、结构证明或反例处置就不放行。留下项必须带关闭条件、承接方和影响。
6. **按原验收合同决定能否退出。** 必验项仍未验证、真实 FAIL 或未偿还事务义务会阻塞对应验收；不能登记为 residual 就自动通过。仅已允许且有理由的范围排除可作为有限范围交付，必须同时披露。
7. **冻结结论证据。** 对齐源码、RTL、build、工具、seed、nodeid 和同轮覆盖；抽查报告反查结果。修改后重开受影响项，而非重写历史 PASS/FAIL。

## 产出

残余记录至少为：`id / 行为或类 / 缺口类别 / 影响 / 证据 / 承接与下一动作 / 是否阻塞 / 接受依据或待决状态`。
这些内容维护在工程既有验证规格、功能点或合同的范围章节；真实缺陷及调查记录维护在
`docs/bugs/`。工程根旧计划已删除，不另建替代计划文件或运行前必填的残余 JSON。

残余分两种写法，不能混用：

- **显式 UNCERTAIN**：用例确实跑过、检查也执行了，但关键依据或覆盖范围不足。用
  Toffee 的 `@pytest.mark.uncertain(reason=..., reference=...)` 声明，判定为 UNCERTAIN，
  不计入 PASS；真实 FAIL/ERROR 永远优先。框架只要求非空原因，引用可选且不限格式；
  需要追溯时引用规格条款或问题 ID。UNCERTAIN 本身不改变退出码，正常退出不等于结论通过。
- **未运行/无法运行**：没有对应用例（端口装不下、本层不负责、组合未构造）。写进残余
  登记，不进任何测试状态。

验收必须考虑两者：必需范围未证明时不能宣称完整硬件通过；UNCERTAIN 不计入 PASS，
也不会把真实失败降级。INCOMPLETE 表示执行、产物或必需验收项尚未完成，不能
拿它与“已执行但证据不足”混用。历史上使用声明式 INCOMPLETE 的运行保留当时判定。

交付摘要应链接实际运行报告、对应规格的未证明范围和问题记录，让评审者能逐项核对。
运行器的 PASS/FAIL 和退出码按实际执行证据解释，不依赖旧计划或另一份残余清单。
出现 FAIL 时保留反例并调查归因，不能只补一条“残余”就当作处置；配置/观察边界也不能
直接当作 RTL 缺陷。历史报告中的残余字段和门禁结果仍按当时版本保留。
`PASS/FAIL/XFAIL/SKIP` 只描述已执行用例，未证明范围是**另一条轴**：不要用 XFAIL 假装它。

| 类别 | 处置，不是自动豁免 |
|---|---|
| 未覆盖功能/组合 | 补用例或明确阻塞 |
| 缺观察点 / 字段宽度不足 | 按 [观察点精度](observation-precision.md) 增加检查路径，或移交并保持未验证 |
| 当前 DUT 边界外 | 说明承接层及其实际验证状态 |
| 仅代码/结构线索 | 列可疑项与所需动态实验，不称已确认缺陷 |
| 证据不足/环境阻塞 | 保存缺失项与重现条件，不称已排除 |
| 明确不适用/范围排除 | 给配置/结构/合同依据和影响，保留审计入口 |

## 如何验收

- 每个必验要求有适用运行及检查证据，或清晰标记为未完成/阻塞。
- 无“残余登记即闭合”、旧覆盖配新结果、PASS 数替代 oracle 等偷换。
- 允许结论是“本轮约定范围达到标准”；不能扩成“没有 bug”或“整个系统已验收”。
- 文档改动只验文档；不借历史仿真证明本次已重跑。

运行证据的具体核对方法见 [归因与证据](../review/triage-and-evidence.md)，案例见 [十二类历史踩坑 P12](../../docs/lessons/rtl-verification-soundness-20261026.md)。
