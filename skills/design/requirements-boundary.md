# 如何定义需求和 DUT 责任边界

## 何时使用、准备什么

新增 DUT、修改功能点或发现越域/漏检时使用。输入是固定版本的需求、微架构合同、真实实例层次、producer/consumer、生成 RTL、参数与导出端口；不能只拿现有测试名作需求清单。

## 怎么做

1. **先写人能理解的行为。** 每项写成“在前提 C 下发生事件 E，应产生结果 R、禁止副作用 F，并在合同规定的时间关系内完成”；再列字段。不要把端口/RTL 分支枚举直接当功能定义。
2. **双向找遗漏。** 一路从需求/历史缺陷推导行为；另一路从端口、状态变化、异常、竞争、失效、复位反查需求。两路对不上时先列缺口，不能按实现反改规范。
3. **沿真实层次分配责任。** 对每项标叶块、上层组合、全核或外部环境；子块结果不能被父块 PASS 替代。跨层行为拆成各层可观察性质，并建立交接关系。
4. **核实合法输入域。** 追到 producer 的编码、对齐、互斥、许可、年龄、撤销/不可撤回点。允许的协议行为要从当前合同取得，不凭接口名字追加保持约束。区分生产可达场景和端口级压力。
5. **逐项选择观察点。** 输出、状态后果、生成产物中的断言分别登记。源码有断言不代表产物保留且启用；间接检查要说明它遗漏什么。内部语义宽于导出端口、字段被裁剪时，按 [观察点精度](observation-precision.md) 扫出“正确性未建立”的字段，不把端口宽度当成需求。
6. **处理边界缺口。** 必需端口缺失不能静默补零。先检查现有合法观察路径；仍不足时记录导出点需求或移交上层，注明承接位置、状态和验证计划。登记移交不等于已经验证，也不授权修改 RTL。

## 产出

责任矩阵至少包含：

| 行为 ID / 语义 | 来源版本/条款 | 本层责任与输入前提 | 观察点/禁止副作用 | 上层承接 | 状态与证据 |
|---|---|---|---|---|---|
| `<行为>` | `<依据>` | `<叶块/组合/全核及条件>` | `<字段/性质>` | `<检查入口或待承接>` | `<已执行/待执行/残余>` |

每个 DUT 合同还要明确单位/地址域、身份、参数、复位、背压、同拍顺序、flush/redirect、异常优先级、可取消边界和时间保证；不适用项给理由。

## 如何验收

- 从需求抽一项，能追到本层检查或明确的上层承接；从一个端口/状态反查，也能找到行为归属。
- 合法输入域有来源；未知编码、缺端口、未承接行为不会自动成为 PASS。
- 分清“当前 DUT 不负责”和“当前没有观测到”；后者仍是验证缺口。
- 矩阵是有界范围说明，不是全部硬件已验证的证明。
