# 如何归因失败并建立可复核证据

## 何时使用、准备什么

出现 FAIL/ERROR、准备修改期望/时序/豁免或宣布缺陷闭合时使用。输入为原始 traceback、日志、实际 nodeid/选择、源码、RTL/build 身份、配置及 seed。

## 怎么做

1. **先保存再改。** 冻结原失败和当时源码/配置，记录要检验的根因假设。新运行用新目录，不能覆盖失败或用当前源码解释旧结果。
2. **沿链反查。** 核实测试实际收集和执行 → 激励合法/前置状态可达 → 全通道采样与事务完成 → 字段确实比较 → oracle 独立且适用 → DUT 是否违反承诺。静态文本搜索只是筛查，不直接构成根因。
3. **做区分性实验。** 最小合法复现配邻近合法控制；修改延迟、相位、模型或驱动后通过，只能先证明相关性。用能排除其他解释的对照确认原因。
4. **限制修复范围。** 修正输入、采样或 oracle 时保持仍受保证的检查；不能用宽泛 XFAIL/skip/waiver 吞掉新原因。strict XFAIL 也不验证失败原因；历史标记须审计，当前策略按工程合同执行。
5. **复验两方向。** 误报修复要证明合法场景不再误报且相邻错误仍检出；漏检修复要证明原错误能被检出且合法场景不被误伤。说明是 checker/模型实验还是真实 RTL 结果。
6. **审计结论证据。** 对齐源版本/源码哈希、RTL、build/原生库、工具、参数、seed、nodeid、日志和同轮覆盖。运行内/运行后源码差异分别记录；缺原件就写缺失，不虚构哈希或重现。审计脚本通过只说明其检查条件满足。

## 产出与结论等级

| 等级 | 最低依据 |
|---|---|
| `confirmed-rtl` | 合法输入下真实 DUT 违反已确认要求，有可重复观察与独立预期 |
| `confirmed-verification` | 激励/环境/oracle/checker 错误有明确证据与修后成对对照 |
| `unconfirmed` | 证据不足，列缺失项及下一实验 |
| `out-of-domain` | 说明当前 DUT 不负责的性质及上层承接，不能称全系统已排除 |
| `ruled-out` | 针对原假设给具体反证与适用范围，不泛化为没有其他缺陷 |

归因记录包括原假设、证明/反证、变更原因、修前与修后运行、注入层、持续检查位置及残余。按独立根因计 bug，失败节点/重复症状数量另列。

## 如何验收

另一位复核者能从结论找到原失败、合同和成对实验。对错 run、缺日志或未选入反例的证据清单，审计应拒绝相应声明；不把文件齐备当语义正确。

案例：[十二类踩坑 P11/P12](../../docs/lessons/rtl-verification-soundness-20261026.md)。退出判断见 [退出与残余](../design/closure-and-residuals.md)。
