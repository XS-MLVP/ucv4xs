# 模块树、身份与生命周期维护（待审核）

## 何时使用、准备什么

用于首次整理模块验证清单、评审切分粒度，或升级源码/配置后出现 top 缺失、模块改名和层次变化。
模块是管理与追踪对象；合同界定验证范围，任务与负责人是模块上的维护信息。
suite 保持代码维护与执行职责，DUT 绑定实际可执行的技术切点。
每个 DUT 独立维护 testbench、环境与测试入口；模块族用于归组，schema2 的实现关联必须一对一。
新增时用 `testbenches/<dut>/`，确认实际共用需求后再按职责提取到 shared。

准备以下输入：

- 旧模块记录及已采用的模块 ID、旧基线、既有 DUT 配方、规格和历史结果入口。
- 目标基线的完整源码/子模块/生成配置，以及能证明生成完整性的凭据；生成后保留 RTL 字节。
- 当前 `ucv info` / workspace 映射和实际实例关系；复用现有材料，但区分旧观察与新证据。
- 本次授权范围：分析、更新本地资料、迁移验证代码、修改线上表分别明确。

没有旧主记录时只能生成首次候选清单；缺少完整目标生成或 internal 来源时，保留“未观察/未核实”，
不能据此认定模块退役。源码路径、行号、生成名、数字后缀、父实例和 suite 名都只能作定位线索。

## 一、先确定值得管理的模块

1. 从设计层次建立模块清单，再将 DUT、规格、testbench、缺口与结果关联到模块。
2. 对具有独立状态、算法、协议或接口的对象评审独立管理价值；复杂父模块仍保留自身记录。
   队列、仲裁、存储、监视设施可以作为子级明细，是否独立派工由实际工作量决定。
3. 深度按对象确定：预测器、运算单元和业务队列可以较细；bank/lane/entry 不按数量自动复制任务。
4. 参数族先提出归并候选。必须核对定义、用途、配置、接口和合同；同源或去掉后缀后同名均不足以证明等价。
   同一族下每个 DUT 的基线、参数、实际选择及结果仍保留。
5. 父模块的整体行为在父模块记录中验收。子模块完成、父级包含、同包维护都不能自动补成覆盖证据。

具体行为与合法域继续使用[需求和 DUT 边界方法](../design/requirements-boundary.md)。

## 二、保存模块身份，再更新每版绑定

采用的模块 ID 一次分配后持久保存。后续改名、源码移动、父级调整和人员变化复用该 ID，
不能每次由当前路径或 RTL 名重新计算。ID 的初始格式不重要，连续性由保存和显式映射保证。

在已有模块记录/关联规格中表达三类信息，避免维护平行的完成度数据库：

| 信息 | 更新原则 |
|---|---|
| 模块身份 | ID、逻辑名称、角色与历史别名；有证据的改名和移动保持身份 |
| 基线绑定 | 该版源码位置、生成 top、实例、配置、DUT；每版可变化，旧记录仍可追溯 |
| 验证证据 | 该基线的合同范围、实际运行、问题和未证明范围；不随名称沿用 PASS |

“未在本次生成出现”“当前未验证”“设计已退役”是不同事实。生命周期处置与验证结果分别说明；
可以由一条主记录承载，无需为每种状态另建管理视图。

树上的主要归属与真实使用位置也分别记录。复用模块可选一个稳定主要归属并关联其他实际实例；
首次使用最近共同上级只是展示建议，新增一个使用点不能自动搬迁主记录或重分配负责人。
对于省略包装层的边，标明间接包含，不冒充 RTL 直接父子关系。

## 三、基线更新先做增量对账

1. 保存旧记录、旧绑定和本次新观察；验证两侧身份、配置及观察完整性。
2. 比较**旧记录与新观察的并集**。仅遍历当前配方会漏掉已从配方撤下的历史对象。
3. 先复用已确认的 ID/别名/基线映射，再以源码历史、角色、接口和父实例提出候选匹配。
   对生成后缀变化、同名异义和多候选保持待核实；名称相似度不能自动批准重绑。
4. 给每条差异明确类别、证据、影响和待办。所有旧 ID 都必须有去向：延续、变化待审或历史保留。
5. 在所属规格中确认范围和承接关系，再更新受影响绑定、资料与必要代码。目录迁移另按维护收益决定。
6. 只对已确定对象实施更新，保留人工维护的负责人、当前工作、阻塞和历史证据。
   草案中的空负责人、初始状态不能覆盖现有值。
7. 读回核验记录、关系和实际改动。按变更影响选择构建/冒烟/功能/覆盖检查，结论各自记录。

## 四、模块“消失”时怎样处理

| 已核实的情况 | 身份和记录处理 | 对验证工作的影响 |
|---|---|---|
| 改名、生成后缀改变 | 复用模块 ID，追加旧新别名与绑定证据 | 检查接口/语义是否变化，再决定复验范围 |
| 模块移动、父级变化 | 复用 ID，保存各版实际位置；审查主要归属 | 模块局部语义与新接入的组合影响分别评估 |
| 参数或接口改变 | 若逻辑角色延续，保留模块 ID，更新变体绑定 | 目标基线标待适配/复验，历史结果保留原范围 |
| 该配置不再实例化或被生成优化消除 | 标明该配置下未独立出现及依据 | 审查可达行为和父级观察；不等于设计永久退役 |
| 功能内联到父模块 | 保留旧记录，注明候选/确认的承接模块与合同条款 | 旧功能逐条确认保留、改变或有依据取消；父级承接仍需证据 |
| 设计拆分、合并或替换 | 按语义决定新 ID，显式记录前身/后继及生效基线 | 新旧合同逐项对应；不按行数或多数结果自动继承完成状态 |
| 有依据的真正退役 | 历史记录可归档，ID 不复用；保留原因和生效基线 | 不改写历史 FAIL，也不把退役写成验证通过 |
| 来源缺失、生成不完整、匹配不唯一 | 标为本次未核实或变化待审，保留上次已知绑定 | 不删行、不猜替代 top、不开始依赖错误绑定的运行 |

**本仓库示例：** CommitQueue 当前不再独立生成，Ftq 有提交逻辑，但旧 CQ 合同的逐条承接仍待审；
TLBNonBlock 当前缺失，现有三种 DTLB 变体是可核查的新切点，不能直接把旧多端口合同改名迁过去。
这些是明确标注的设计案例，不作为其他工程的固定层次或自动映射规则。

## 五、工具与 Skill 各自承担什么

- 工作流入口负责基线、资源和运行；本方法约束如何作身份与变更决定。
- 确定性工具适合核对输入哈希、层次、唯一映射、孤立记录、实际差异及读回结果。
- Agent/维护者需要依据设计资料判断模块是否延续、是否值得归并、合同由谁承接；证据不足保留待审。
- 线上表操作按实际产品 Skill 执行。导入文本父 ID 不代表已建立关联，更不代表原生折叠树已配置。
  先确认当前能力和授权范围，再使用真实记录 ID 更新与读回。

当前 `ucv modules list/check/adopt/diff/apply` 已实现离线身份和增量维护，输入是核实后的规范化观察；
格式、前后值、冲突保护和读回流程见[命令契约](../../docs/reference/modules.md)。
首次采用后必须沿用持久目录，不重新运行原日期草案脚本覆盖主记录。新 DUT 用
`ucv init --module-id <id>` 关联身份，同族也生成独立 testbench。已有 `info/check/docs`
继续导航实际配方和规格；线上表同步与自动语义承接不属于这些命令。
文件存在不表示本方法已注册到 Agent 客户端。

## 产出放在哪里

- 一次评审的旧新观察、变化提案、输入身份和核验日志放新的结果目录。
- 模块范围、功能点、承接条款和正式处置回到已有设计/验证规格；问题沿用稳定问题记录。
- 若采用外部模块主表，模块 ID、当前维护字段和线上 recordId 映射沿用该主记录，保留可恢复导出。
- 不恢复 `verification_plan.json` 或改名替代它；不为切分本身新增一份功能完成率计划。

## 如何验收维护效果

- 所有旧 ID 和既有 DUT 可追溯；退出当前活动范围有明确处置，不靠静默消失。
- 模块改名/移动后 ID 和人工字段保持；拆分/合并的前身后继关系可查。
- 每个当前绑定与其实际基线、配置、接口对应；同名和参数族不会跨版本冒领结果。
- 管理父级和实际使用关系明确，树无环、引用有效、每项证据指向正确对象。
- 不完整观察不会触发删除；多候选不会自动改绑；旧 PASS 不成为新基线 PASS。
- 在工具正式用于增量更新前，必须覆盖改名/移动、内联、拆分、缺失来源和人工字段保留等迁移对照。

工具的迁移对照采用合成基线，真实设计的跨基线合同承接仍需后续核查。已核查的案例、草案局限和证据见
[模块切分与维护复盘](../../docs/lessons/module-splitting-and-maintenance-20261117.md)。
