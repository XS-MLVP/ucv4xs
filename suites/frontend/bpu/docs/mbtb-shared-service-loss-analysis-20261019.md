# 两个已接纳的工作不能因为找回同一服务主人而丢失

补强既有 BPU-MBTB-026，不增加功能编号。义务在开发前写于
`mbtb-shared-service-owner-contract.json`：容量足够、目标记录不同的目标纠正与失效清理，各自保留直至服务。

## 为什么旧通过没有证明这个组合

旧清理并发场景把正常纠正和清理分在不同的服务主人；旧迟到重放场景没有同拍清理。
分别通过不等于组合通过。Main 的“请求建议写到哪里”和“完整逻辑记录目前归谁服务”也不能混用。

独立参考另有盲点：它从同一份旧空闲集合分别选位置，可把两笔工作都放在第一个空位。
纯事务反例原先 12 FAIL / 8 PASS，修正为先保留本拍命中项、再分配新义务后，相关178项纯测试全通过。
这是加强参考，不是修改RTL，也不是把参考放宽为硬件现状。

## 原生观察

四份不同的真实冷预测先于学习取得，初始化只使用其中两份，另外两份留到迟到反馈；不重复把同一次解析当成新原件。
用正常训练建立两个重复版本与另一行的分支，正确跳转触碰让迟到冷原件提出另一写入位置，但完整记录仍保留原主人。
公开反馈接纳事件通过已有 `CycleMonitor` / XReactor `on` 订阅释放一次S2消费，测试用例不包含时钟边沿或底层IO操作。

正式测量中，两个不同目标的完整请求在同一拍到达。只读 memory-direct 前态显示原记录已完成服务，两个保留位置的 dirty 均为0。
两项本来都能留下，但实际仅服务失效，目标纠正丢失。随后正常公开查询的独立参考比较中，只有 `1.target` 不同：
仍是旧目标，预期应比它增加 `0x800`。其他完整字段相同，排除了这里依赖旧负方向邻居错误才能失败的情况。

普通身份及仅tag为零的身份均失败；两个不共享服务主人的控制均通过。首次请求同拍、完整输入、容量前态、缺失服务和错误消费者共同构成证据。
最初启动探针中的准备错误和不同拍不计为RTL错误；正式四程序已逐项通过这些前提核验。

## 源码归因

`XiangShan/src/main/scala/xiangshan/frontend/bpu/WriteBuffer.scala:186` 从旧 dirty 状态选空位，
`:195` 的新建项和 `:213` 的已服务命中项分别修改 nextEntries，却没有先预留同拍命中项。
生成的 `rtl/bpu/WriteBuffer_4.sv:563` 对后一个输入的赋值优先，能够压过前一个输入找回原主人的修改。
结合实际前态和服务轨迹，符合“后一个新建清理覆盖刚被修改的已服务记录”的解释；不声称全部41个开放行均由此导致。
