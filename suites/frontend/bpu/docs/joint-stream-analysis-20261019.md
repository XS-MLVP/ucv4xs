# 排队旧反馈等待时，预测继续前进，两个学习者不能偷跑

## 先纠正一处验证思路错误

上一轮前沿提示把“有效非零循环下TAGE/SC共同学习”继续列成待验证，但精确归档中已有INT-106四个PASS和INT-107十六个双原件PASS，且相关源码仍逐项匹配冻结版本。它们早已包含实际学习、完整训练读取和新预测数值消费；不能因为摘要过时就重复开发同一功能。

本轮重读源码和原始JUnit后，纠正了条件经验要求层的过时限制：不再说这些程序只验证IMLI=0、没有共同学习或没有最终数值组合采样。要求仍是41条稳定的人类语义，不新增“某根信号变了”功能编号。

真正缺的组合是：旧双反馈程序暂停了预测，单反馈持续预测程序又不含已排队的第二原件。先定义[新契约](bpu-joint-stream-contract.json)，只补强INT-107，全部旧contract、其余352个定义及旧16项对照均保持。

## 人能理解的要求

两份真实旧结果都已提交时，预测还在继续向前。队首因读取冲突暂时不能接收，此时方向和纠偏学习都不能偷偷接受它，队尾也不能越过去；但年轻预测必须真的消费自己的非零经验。

停止新预测以解除实际冲突后，两份旧结果各接受一次，各自产生完整的方向和五家族纠偏效果。它们仍需实际交叠，不允许把两份学习偷偷串行化后通过检查。随后重新走到两个原迭代，分别消费共享经验与各自的私有经验。

早期有效/稳定循环、年轻实际继续/退出、原件正序/逆序返回组成8个程序。全部先用正常真实反馈建立非零经验，没有bank/set/way遍历；原件完整metadata、十九个折叠历史及九类原快照均保持。

## 如何验证及首轮错误

复用现有公共反馈driver、静态MEM_DIRECT bundle、七个独立语义模型和pipeline monitor，不新增框架层hack，也不改参考算法。等待结束由实际冲突事件决定，case没有IO、边沿、固定周期或gather。

首轮8项失败在新增检查器：数值证明以检查点序号为键，我却按预测序号查找，因此漏掉实际消费者。两个计数器并不相同。修正关联键，补上刻意使用不同序号的正反例，再重新冻结和执行；没有缩小消费者要求，也未登记RTL缺陷或XFAIL。
