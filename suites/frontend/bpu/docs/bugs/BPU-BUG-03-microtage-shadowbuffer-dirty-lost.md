# BPU-BUG-03：MicroTAGE 用过期槽号清掉了另一条分支的新学习

连续反馈到来时，写缓冲会复用旧槽位。一条反馈提前记住“旧版本在哪个槽”，等它真正清理时，这个槽可能已经装入另一条分支的新版本。当前实现仍按旧槽号清除待写标志，导致另一条分支的学习无法写入预测表。

状态：模块丢更新机理已定位，相邻反馈失败、串行对照通过。尚未证明这条完整历史与反馈序列能由真实 SoC 生成，不能将模块复现直接当作 SoC 缺陷确认。

## 怎样触发

代表用例用固定 PC、8 种历史形成 8 个学习对象，通过正常训练建立记录，再按相反顺序奖励它们。相邻反馈让前一条的写入与后一条的查找重叠。

把其中两条称为 A、B：

1. 缓冲槽 3 原来保存 B，B 对应预测表索引 2。
2. A 的奖励写入槽 3，将它改为 A 的新版本；A 对应预测表索引 6，方向计数为 5。
3. 与这次写入重叠的 B 查询仍取得旧槽号 3，并把它带入下一训练阶段。
4. B 更新时，槽 3 实际已经属于 A，但清理逻辑仍把槽 3 的 `dirty` 清零。
5. A 的新版本不再发出存储写入，回读 A 时仍得到旧计数 4。

`dirty` 表示该槽有尚未写入预测表的内容。把它清零不是只删一条诊断记录，而是取消了相应的待写学习。

## 直接观测

2026-10-22 的 memory-direct 复核得到以下顺序。tick 是仿真事件编号，不是周期数。

| tick | 正在更新的对象 | 槽 3 的实际内容 | 槽 3 的 dirty |
|---|---|---|---:|
| 485 | A：索引 6；写入槽 3 | 写入前仍是 B，索引 2、计数 4 | 0 |
| 487 | B：索引 2；要求清理槽 3 | 已是 A，索引 6、计数 5 | 1 |
| 489 | 下一条反馈 | 仍是 A，索引 6、计数 5 | 0 |

最终 `(1, 6).counter` 预期 5、实际 4。测试观察到 24 次反馈接收、24 个学习版本、23 次实际存储写入，与这条被错误取消的更新吻合。

同一工作集和学习顺序，改成串行反馈后通过。因此这里不是仅凭“发布次数减服务次数”推断丢失。

## 根因在哪里

[BypassShadowBuffer.scala](../../XiangShan/src/main/scala/xiangshan/frontend/bpu/utage/BypassShadowBuffer.scala) 把 T0 查到的清理槽号寄存到 `t1_cleanId`，但稍后的操作直接使用这个槽号：

```scala
when(t1_hasWrite && t1_hasHit) {
  statusEntries(t1_cleanId).dirty := false.B
}
```

它没有重新确认该槽仍属于要清理的旧版本。现有旁路主要处理相邻反馈索引相同的情况，不能解决“不同索引复用同一个槽”的冲突。

需要保证清理针对旧版本的身份，而不是只认一个已经可能过期的槽号。仅调整同拍赋值先后，不能解决本例。

## 与旧归因的区别

本例并非“新写入槽号等于同拍清理槽号，自己把自己清掉”。实际是后一条反馈用过期槽号，清掉前一条刚写入的其他对象。旧归因只看赋值优先级，没有追踪槽位内容的变化。

确认范围是下方最小场景；早期关联的 17 个 FAIL 仍需分别确认，不能全算作同因。

## 上游输入审核

测试把历史值和反馈顺序直接提供给 MicroTAGE。真实输入来自 PHR 及 BPU 同一预测实例，且 S1 首跳之后的元数据会被裁剪；不能独立指定任意历史、任意反馈次序。

目前没有证明真实 S3 流能产生本例的整条槽复用顺序，也没有发现足以证明它永远不会发生的约束。因此保留已观察到的过期槽号问题，但不将它列为已经证明 SoC 可达的缺陷。详见[输入契约](input-contracts.md)。
