# 生产回归与物理深度回归

默认运行生产回归：

```sh
python -m tools.refresh_coverage --workers 64
```

需要完整 ABTB bank/set 遍历时显式运行：

```sh
python -m tools.refresh_coverage --regression-profile physical --workers 64
```

直接使用 pytest 时同样适用 `--regression-profile`，默认 `production`。
三类集成 ABTB 场景默认各使用 bank0/set0 一个代表，共 3 项；
`physical` 在 4 bank × 64 set 重复同样的检查，共 768 项。
其余 DUT、场景、检查和已知严格 XFAIL 保持不变。这不是跳过 765 项测试，
而是在收集阶段选择明确的回归范围，不能把生产回归宣称为物理遍历全满。

## 门禁与报告

- 两种范围都必须通过三类原因 × 四个 way × 四个转换/饱和保持，共 48 个语义 bin。
- 物理矩阵仍为 1024 cell × 12 path = 12288 bin。两种报告都保留完整分母和未命中项；
  只有 `physical` 要求全部命中。reset/priority 矩阵也完整保留，不声称已经关闭。
- 其余既有功能矩阵门禁不放宽，功能点仍须逐项实际执行。
- 原生 LCOV 的 SF/DA 行分母不变，不裁掉未遍历物理实例。
- 同一范围的后续回归禁止丢失已命中行。首次生产范围建立独立基线，
  相对历史遍历范围减少的行会完整计入 `native-scope-comparison.json`，不称为覆盖率提升。
- `results/regression-profiles/{production,physical}/latest.json` 分别指向通过门禁的完整回归。
  切换默认发布前保留旧发布视图；深度回归的旧物理基线不会被生产范围替换。
- `--select` 仍只生成选定范围报告，不建立完整回归基线，也不覆盖默认发布。

覆盖缺口必须进一步归因：物理复制未遍历、缺失的功能场景、已确认 RTL 缺陷、
有证据的不可达条件分别记录；不能通过删分母或枚举坐标替代功能场景设计。

## 批量开发与全量验收

每轮先集中开发多个语义场景，再做一次完整生产回归。通常以 3 至 5 个有独立
判别意义的真实 DUT 场景作为开发批次的工作目标，不设凑数门槛；同一生命周期
问题的前态、竞争与后续消费者应尽量一起完成。纯模型测试、负对照及夹具检查
分别计数，不把它们算成新增 DUT 场景，也不通过扩大 bank/set 枚举凑批次。

开发期间按改动范围运行定向回归：先检查独立参考和判错能力，再验证新 DUT
场景；driver、monitor、agent 或共享模型发生改动时，同时运行其已有兼容用例
和受影响的 DUT 场景。先在定向阶段处理接口与时序问题，避免每加一个用例、
每修一个接口就启动全量。已知失败保留原判定，新失败不能用跳过或扩大 XFAIL
范围隐藏。

批次内场景及公共接口稳定后，冻结源码并统一执行完整生产回归，比较原有判定、
功能事件和原生行命中集合。冻结后又改动验证源码时，旧结果只对应旧版本，
不能当作新版本的完整验收；应先把同批剩余修改及定向检查做完，再重跑全量。
定向结果始终只代表选定范围，不提前更新完整回归结论。

新增功能 ID 时，所有直接读取 `verification_plan.json` 的测试都应纳入定向
影响范围，而不只运行新模块及统一分域测试。模块本地检查核对自己负责的
明确身份集合和证据绑定，不写死其他模块也共享的全仓总数；全局身份及分域
仍由统一计划检查负责。纯检查或要求字段归一化在完整测量后修复时，单独
保留专项及源码差分，不将两次不同版本的结果拼成一份不存在的全量报告。

每轮汇报新增真实 DUT 场景数、覆盖的语义要求、定向结果及完整回归次数；
只有消费者与比较全部成功的事件才能记为 checked。覆盖率没有增长时，区分
判错能力增强、已知失败阻断和仍缺功能场景，不以测试数量代替验证进展。

## 训练完成语义

`train` / `train_batch` 确认提交，并保留默认预测流行为；同 bank 持续读时，
应传入 `prediction_pause=True`，由 agent 建立读空窗，不能靠超长等待假装会提交。
`train_batches` 保留预测流并等待反馈流水线退休；同 bank 持续读时，SRAM 写缓冲可以合法保持 pending。
`train_batches_with_prediction_pause` / `train_batch_with_prediction_pause` 建立读空窗并确认写入提交。
需要显式提交门禁时使用 `wait_training(committed=True)`，调用者须先消除读压力。
用于随后检查更新状态的 `train_batches_during_stream` 要求 bank 不冲突，并确认提交。
这些都是状态条件，不是增加固定等待周期。
