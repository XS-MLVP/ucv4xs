# DEQ-WB-001：写回结果还没被接收，错误标志就消失了

**结论：已确认的RTL bug；未完成修复复测。** 固定版本为公开`kunminghu-v3 @ 893e1580b705d81f113c30c7a05734e09a08050e`。原两次回归的去重并集中，有50个失败节点属于这个根因，不是50个独立bug。

## 1. 用一句话理解

总线已经告诉Store“这次访问出错了”，但后端暂时没空接收结果。RTL没有把错误保存到真正交接，而是在等待过程中自行清零。等后端终于接收时，看到的结果反而是“没有错误”。

可以类比为：快递单已经标了“包裹损坏”，收件人还没签收，系统就把损坏标记擦掉了。

## 2. 正常应该怎样工作

`DeqModule`负责向后端报告部分Store/CBO的完成情况。响应中的：

- `denied=1`：访问被拒绝，应该报告Store访问错误。
- `corrupt=1`：返回硬件错误信息，应该报告相应硬件错误。
- `writeBack.valid=1`：结果已经准备好。
- `writeBack.ready=0`：后端暂时不能接收。

只有`valid && ready`同时为1才真正交接。在此之前，原请求的错误信息不能丢失。

## 4. 怎样激励

以下以已有的CBO响应错误测试为例：

1. 给一个已获许可、地址/数据齐全的非zero CBO。
2. 让Sbuffer排空，使CBO请求实际被DCache接受。
3. DCache返回响应，例如`corrupt=1、denied=0`，并确认响应真的`fire`。
4. 保持`writeBack.ready=0`，让写回结果至少等待一个额外时钟。
5. 再把`writeBack.ready`置1，检查**实际写回交接**中的错误位。

| 时刻 | 正确结果 | 原RTL实际表现 |
|---|---|---|
| 刚接受错误响应 | 进入写回，错误位为1 | 首次有效写回的错误位确实为1 |
| 写回被背压一个时钟后 | `valid=1`，错误位仍为1 | `valid=1`，错误位被清为0 |
| 最终`writeBack.fire` | 后端接收到原来的错误 | 后端接收到错误位0 |

测试也覆盖`denied`以及两种错误同时出现。这里没有要求后端永远不接收，也不是比较无效payload。

## 5. 为什么这是RTL问题

进入`writeback`状态后，两个`.elsewhen`无条件安排在下个时钟把错误清零。若后端背压，状态继续停在`writeback`，于是出现“完成有效位还在，完成内容变了”的错误。

不能用“实际后端总是ready”排除此反例：`MemBlock.scala:1028–1034`有Store写回的流水和仲裁，`ready`不是常量1。

## 6. 后果和证明边界

- **已经观察到**：有效写回在背压期间丢失错误，最终`fire`也丢失错误；异常信息输出使用同一份错误状态。
- **风险**：后端可能把一次本应报错的访问当作正常完成，或者失去正确的异常处理信息。
- **没有声称**：这份模块报告已经完成整核异常程序的ISA复现。

修复方向是让错误状态属于原请求，并保持到该请求真正写回或被协议允许地终止；不能让参考模型也跟着提前清零来“修复测试”。
