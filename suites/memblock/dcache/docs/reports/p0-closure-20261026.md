## 2. 逐项

### 2.1 `MQ-STORE-MERGE-DATA-PENDING`：确认 RTL 缺陷

**复现**：同一行两笔部分 store，第一笔写 byte0=0xAA（mask 0x01），第二笔写
byte1=0xBB（mask 0x02）。第二笔被受理（`queryMQ ready=1`、`handled=1`、无第二次
Acquire），说明设计意图是合并。

**观测**：

| 层 | 观测 | 期望 |
|---|---|---|
| MissQueue 独立 UT | `refill_info.store_data` 低 16 位 = 0x01AA | 0xBBAA |
| DCache 顶层（真实 DUT） | 安装行低 16 位 = 0x00AA | 0xBBAA |

两种观测都说明第二笔 store 的字节没有进入 `refill_and_store_data`；顶层还把 L2 的
byte1 覆盖成 0x00。

**根因定位**：`MissEntry.sv` 中该寄存器的 store 合并分支与 `req_store_mask` 更新都由
`_GEN_1 = io_miss_req_pipe_reg_merge & (io_miss_req_pipe_reg_req_source == 4'h1)`
门控。第二笔 store 走的是 entry 级合并（`MissQueue.scala:888` 的
`before_data_refill_can_merge`：`!main_pipe_refill_resp && !w_refill_resp &&
new_req.isFromStore && alloc_is_store`），此时 `miss_req_pipe_reg` 上的 `merge`/`req_source`
并不指示“这笔是 store 合并”，因此数据/掩码分支不执行。

**用例**（都是严格 `xfail`，修复后会自动变成 unexpected pass）：

- `tests/miss_queue/test_miss_queue.py::test_second_store_merge_carries_its_bytes`
- `tests/dcache/test_dcache.py::test_two_partial_stores_same_missing_line_merge_data`

**影响**：真实功能缺陷（静默丢写 + 错误成功响应）。相关功能点文档已加“已知缺陷”段，
不再把该行为算作已验证。

### 2.2 `DCACHE-DENIED-ERROR-PADDR-ZERO`：不是缺陷

MainPipe 用 `Cat(s2_tag, get_untag(vaddr))` 重建上报地址（`MainPipe.scala:682`）。
冷行 tag 为 0，因此只剩 `vaddr[11:0]`：

| 地址 | `io_error.paddr` | `report_to_beu` |
|---|---|---|
| 0x11000 | 0x0 | 0 |
| 0x11440 | 0x440 | 0 |
| 0x123C0 | 0x3C0 | 0 |

原来的“paddr=0”只是因为测试地址页对齐。`report_to_beu` 只对 tag/data ECC 错误置 1，
L2 denied/corrupt 时 BEU 不消费该字段。

**用例**：`test_denied_refill_error_paddr_is_vaddr_low_bits`（普通通过，固化契约）。

### 2.3 `BDA-ECC-DELAYED-FLAG`：不是缺陷

| 场景 | 数据 | 8 个 `read_error_delayed` |
|---|---|---|
| 从未写过的 set/way | 0x8b8e / 0xebb1 / …（随机） | 全 1 |
| 经编码器写全零后 | 全 0 | 全 0 |
| 写其它地址后 | 符合模型 | 全 0 |

未写过的 SRAM 行数据与 ECC 无对应关系，解码必然报错，这是 ECC 的正常检测结果。
BDA 的用例本来就先 `prime` 再用编码写路径初始化，因此“正确数据也报错”的旧结论撤回。

**用例**：新增 `test_zero_line_has_no_ecc_error`；`test_ecc_error_flag_clears_after_read`
与 `test_readline_data_and_flag_clear` 现在断言 `error_delayed == 0`（原先只断言读后回 0）。

### 2.4 `CF-DEQUEUE-PIPELINE-NO-RESET`：新发现（系统内良性）

**发现方式**：多 seed 扫描。seed=1 全过，seed=2 时 4 个确定性用例失败
（`test_single_entry_lifetime` 等），报“query 期望命中而 DUT 不命中”。同一份激励只
差 Verilator 随机初值，说明有状态未复位。

**定位**：`CounterFilter.sv:606-610` 的 3 级出队计数流水
`last3CycleAlloc_REG/_REG_1/_REG_2` 在无复位的 `always @(posedge clock)` 块里，只有
末级 `last3CycleAlloc` 被复位。短复位后第一个时钟沿按旧值出队，把 `deqPtr` 推过
`enqPtr`，FIFO 永久偏移。

**处理**：env 的 `reset()` 改为保持复位 5 拍（期间输入全 0）再释放，让该流水在指针
被 clamp 期间冲干净。seed 1/2/3/4 全部通过。

**影响**：真实系统复位持续数百拍，且 DCache 复位后要等 256 拍 SRAM 清扫才会发 load，
流水早已清零，因此对功能无影响。仅影响“复位后立刻打流量”的仿真。

### 2.5 `DCACHE-REEVICT-BLOCK-REJECTED`：是写回阻塞契约，不是缺陷

**初始观测**：4 个 way 填满同一 set 后访问第 5 个 block 触发替换；此后再次访问被替换
的 block，load 恒为 `miss=1, handled=0`，store 恒为 `replay=1`。等待 0/50/400 周期
都不恢复，看起来像“永久拒绝”。

**根因**：测试环境的 `DcacheEnv._idle()` 默认把 `c_ready` 清 0，替换产生的 C 通道
Release 从未被接受，因此 WritebackQueue 条目一直占用该 block；MissQueue 通过
`io_block_miss_req` 拒绝为同一 block 分配新 MSHR。这正是设计契约：
`handled=0` 表示“请 replay”。

**验证**：新增用例 `test_pending_release_blocks_remiss_until_drained`：

1. 填满 4 way → 访问第 5 个 block（`c_ready=0`）触发替换；
2. 对被替换 block 的 load 得到 `miss=1, handled=0`；
3. `c_ready=1` 并回 ReleaseAck；
4. 同一 block 的 load 得到 `miss=1, handled=1` 并完成 refill。

**结论**：不是缺陷。真实 L2 会接受写回并回 ack，LSU 会把 `handled=0` 当 replay 重发。
随机流量生成器现在保持 L2 侧常开（`ack_ready`）并在 `handled=0` 时重试，替换语义由
定向用例覆盖。

**顺带修正**：`DcacheEnv` 的默认 `c_ready=0` 语义本身没问题（避免意外接受写回），
但所有需要替换的场景必须显式打开 C 通道或持续 ack——这条已写入
`docs/functional-points-dcache.md` 的 DC-FP-004。

## 3. 多 seed 与随机流量

### 3.1 Python 侧随机也可复现

新增 `conftest.py` 的 `deterministic_test_seed`：`random.seed(DCACHE_TEST_RANDOM_SEED)`；
`tools/run.py` 把 Verilator seed 与 Python seed 一起写进 `results/<run>/seed.json`。
此前只有 Verilator seed 可控，Python 随机用例不可复现。

### 3.2 约束随机流量

`tests/dcache/random_traffic.py` + `test_constrained_random_load_store_traffic`：
L2 shadow memory + 未写回 store 字节模型，每笔 load 比对 8 字节窗口，每笔 C 通道
release 在并入模型前比对数据。单次 36 操作，覆盖 hit/miss/refill/store 掩码混合。

生成器的两条明确边界（写在文件头）：

1. 不对同一未完成 miss 的行发第二笔 store（避开 2.1 的缺陷）；
2. 不访问已被替换的 block（避开 2.5 的未定位问题）。

## 6. 本轮的方法学收获

1. **“看起来卡死”先检查激励**：两个“永久拒绝”的观测（reevict、BDA ECC）最终都是
   环境没有履行协议（C 通道未放行 / 读到未初始化 SRAM），而不是 RTL 缺陷。
2. **多 seed 是必须的**：CounterFilter 的无复位流水只在 seed≠1 时暴露；单 seed 通过
   会给出错误的稳定性结论。现在 `tools/seed_sweep.sh` 是标准流程。
3. **缺陷要能用两种层次复现**：store-merge 在 MissQueue 独立 UT（`0x01AA`）和
   DCache 顶层（`0x00AA`）分别复现，才能排除驱动错误并定位到 `MissEntry` 的合并
   门控条件。
4. **严格 xfail 是缺陷的活文档**：修复后自动变成 unexpected pass，强制重新审视
   功能点与覆盖率归因。
