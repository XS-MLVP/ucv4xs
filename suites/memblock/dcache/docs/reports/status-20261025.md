### 3.2 前期功能点复核

`docs/reports/functional-point-audit-20261025.md`，修正 7 项实质错误：

1. BDA 地址函数写成 `addr[10:6]`（正确是 `addr[5:1]`）；
2. BDA ECC 声称"正确数据 `error_delayed=0`"（当时实际相反，且用例从未断言）；
3. MainPipe 声称 AMO miss 当拍返回 `miss=1`（实际 miss 当拍无响应，只有 replay
   路径响应且 `miss==replay`）；
4. MissTrack 声称事件有固定优先级（实际同 line 合并、不同 line 走 RRArbiter）；
5. WritebackQueue 的 opcode 附加了错误的 `param=0` 条件；
6. DCache 顶层 Acquire opcode 含糊（load 恒 6，7 只用于整行 store）；
7. MainPipe "整字不读行"过窄（判据是所有被写 bank 都整 bank 覆盖）。

### 3.5 覆盖率补强（2026-10-26 第二轮）

上一轮交付后有人问"为什么 DCache/MissQueue 覆盖率这么低"，定位结果是**激励没覆盖
状态空间**，不是功能缺失：

- `test_all_sets_all_ways_update_replacement_state`：填满 256 set × 4 way（1024 行），
  再按 4 个 touch 端口各扫一遍。原来只碰少数 set 且只用 lane 0，导致按 set×way 展开的
  meta 阵列、按端口展开的替换状态优先级链各有 50% 以上没执行。
  `L1ErrorMetaArray` 72.5%→100%、`L1CohMetaArray` 76.1%→100%、`DcacheDut.v` 52.3%→99.4%。
- `test_same_cycle_ports_touch_one_set`、`test_store_misses_on_every_query_port`、
  `test_three_ports_merge_into_one_entry`、`test_eight_consecutive_store_misses`：
  补多端口记账分支。

DCache 行覆盖 **69.99% → 98.20%**（+14808 行），MissQueue **87.90% → 88.28%**。

### 3.6 prefetch 标记路径（2026-10-26 第三轮）

上一轮把两张 prefetch 表（2072 行）归因为"prefetch 未建模"。复查发现**可以从公开端口
驱动**：`io_prefetch_req` 是 MainPipe 的独立输入，`pf_source > 1` 即
`isFromL1Prefetch`；装入后一笔 demand load 命中会触发 `prefetch_flag_write` 把标记清为
`L1_HW_PREFETCH_CLEAR`。

新增 `test_prefetch_install_then_demand_hit_clears_flag`：对 256 set × 4 way 逐条做
"预取装入 → demand 命中 → 清标记"。`L1PrefetchSourceArray` 83.6% → **99.86%**、
`L1RefillLatencyArray` 83.4% → **99.86%**，DCache 顶层 94.11% → **98.20%**。
至此顶层只剩 919 行，全部是内联子模块的重复计数。
