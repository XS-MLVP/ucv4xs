## 4. 为什么这几个数字不是 100%

### 4.1 DCache 顶层：919 行，全部是“重复计数”

| 类别 | 行数 | 说明 |
|---|---:|---|
| 内联子模块（各自已有独立 UT） | **919** | MainPipe 281、MissQueue 241、CounterFilter 90、`DcacheDut.v` 67、`NewPipelineConnectPipe_9` 64、CtrlUnit 42、BankedDataArray 32、其它 ~100 |
| 两张 prefetch 元数据表 | **9 + 9** | `L1PrefetchSourceArray` 6298/6307、`L1RefillLatencyArray` 6214/6223 |

**为什么现在能说“不是功能缺口”**：这两个 prefetch 表之前缺 2072 行，原因是没人驱动
`io_prefetch_req`。这条路径完全可以从 DCache 的公开端口驱动：

- `io_prefetch_req` 是 MainPipe 的独立输入（`MainPipe.scala:276`
  `prefetch_req.bits := convertPrefetchReq(io.prefetch_req.bits)`），带
  `paddr/vaddr/pf_source`；
- `pf_source > 1`（`L1_HW_PREFETCH_CLEAR`）即 `isFromL1Prefetch`，装入的行带
  prefetch 标记；
- 之后一笔**非预取 demand load 命中**该行时，`LoadPipe` 触发
  `prefetch_flag_write`（`s3_clear_pf_flag_en`）把标记改写为 `L1_HW_PREFETCH_CLEAR`。

新用例 `test_prefetch_install_then_demand_hit_clears_flag` 对 256 set × 4 way
逐条执行“预取装入 → demand 命中 → 清标记”，因此所有按 (set, way) 展开的写/读/清臂都
被执行：两张表从 83.6% / 83.4% 提升到 **99.86% / 99.86%**（各剩 9 行声明/默认臂）。

### 4.2 内联子模块的 919 行：不是 DCache 的缺口

DCache 构建内联了 MainPipe、MissQueue 等子模块，这些行在**各自的 DUT 构建**里已经
单独统计（MainPipe 100%、MissQueue 88.3%…）。把它们计入顶层是重复计数，因此顶层
98.20% 的剩余 1.8% 里没有一行是“DCache 独有行为未验证”。

### 4.3 MissQueue：246 行

| 类别 | 行数 | 分类 | 原因 |
|---|---:|---|---|
| `s1RespDataFwd_*` / `s1RespMask_stLdFwd_*` | 80 | **范围限制** | store→load 转发寄存器，由 `io.forward_*` / `io.forward_stData` 驱动，属于 Sbuffer/LoadPipe 联合场景，不在 MissQueue 的 MSHR 语义内 |
| 默认 `else` 臂 | 36 | 工具/生成代码限制 | 优先级链的兜底分支，合法输入下不可达（父块保证至少一个 valid） |
| `source_except_load_cnt` 深层链 | 26 | 情形缺失（部分） | 4 个 `queryMQ` 口的复位/自增优先级链；单口激励只走顶层臂。已加四口轮转用例，剩下的是多口同拍的组合 |
| `parallel_pipe_regs_N_mshr_id` | 19 | 情形缺失（部分） | 多口 merge 到同一 entry 的更深组合 |
| 三元默认值 / 其它 | 32 | 混合 | 常量折叠臂、声明行 |
| 声明行 | 53 | — | wire/reg 声明，不是可执行语句 |

**没有“整体功能点缺失”**：7 个功能组全 100%，MSHR 分配/合并/refill/安装/Finish、
probe/replace 阻塞、CMO、错误上报、多 release 槽位都有行为断言。

### 4.4 补例前后的实际变化（这一轮做的事）

| 阶段 | DCache 行 | MissQueue 行 | 做了什么 |
|---|---:|---:|---|
| `full-regression-09` | 35452/51179 = 69.3% | 1673/2099 = 79.7% | 基线（定向用例） |
| `full-regression-11` | 35820/51179 = 70.0% | 1845/2099 = 87.9% | 多口 merge、写回阻塞、约束随机、store-merge 缺陷复现 |
| `full-regression-14` | 48167/51179 = 94.1% | 1853/2099 = 88.3% | 256 set × 4 way + 4 端口扫描 |
| **`full-regression-15`** | **50260/51179 = 98.2%** | **1853/2099 = 88.3%** | 再补 `io_prefetch_req` 预取装入 + demand 清标记扫描（见 4.1） |

关键的两个新用例（都不是“为了覆盖率灌激励”，而是补真实情形）：

1. `test_all_sets_all_ways_update_replacement_state`
   —— 填满 256 set × 4 way（1024 行），再按 **4 个 touch 端口各扫一遍**。
   原因：meta/flag 阵列的读写译码按 (set, way) 展开，替换状态更新按“端口优先级”
   展开（mainPipe > lane2 > lane1 > lane0）。定向用例只碰过少数 set 且只用 lane 0，
   所以 4 个阵列各缺 50% 以上。同一 set 用两个端口同拍 touch 不可能（同 index 即同
   bank，被 bank-conflict 仲裁掉），因此用“单端口逐遍扫描”覆盖 4 个优先级臂。
   效果：`L1ErrorMetaArray` 72.5%→**100%**、`L1CohMetaArray` 76.1%→**100%**、
   `L1PrefetchSourceArray` 52.0%→83.6%、`DcacheDut.v` 52.3%→**99.4%**。
2. `test_prefetch_install_then_demand_hit_clears_flag`
   —— 通过 `io_prefetch_req` 对 256 set × 4 way 逐条“预取装入 → demand 命中清标记”。
   这是唯一能驱动 `prefetch_flag_write` 的路径（load 侧的 `pf_source` 被折叠掉），
   一次性把两张 prefetch 表从 83.6% 推到 99.86%。
3. `test_same_cycle_ports_touch_one_set` + `test_store_misses_on_every_query_port`
   —— 补齐多端口同拍与四口轮转的记账分支。

### 4.5 ProbeQueue 的 4 行

全是声明行（`ProbeEntry.sv` / `ProbeQueue.sv` 的 wire/reg 声明），过程语句无缺口。
它的分支覆盖 60/96 = 62.5% 偏低，是因为 `pipe_resp` 由父块 perf 事件驱动，独立 DUT
里无法完整驱动响应侧；该语义由 DCache 顶层的 `test_probe_ack` 覆盖。

### 4.6 Toggle 45~47%

未翻转点集中在：48-bit paddr、50-bit vaddr、512-bit 数据、16 项 MSHR 宽状态、42 个
perf 计数器高位、未激活的 forward/spec 端口。功能检查按字段/字节比对，不要求每个
数据位双向翻转。**不作通过标准。**

## 6. 磁盘占用（为什么之前是 1.1 GB）

`results/` 一度是 1.1 GB，构成与处理：

| 内容 | 单份大小 | 说明 |
|---|---:|---|
| `native/<build>/coverage.dat` | 86 MB（DCache）/ 73 MB（wrapper）/ 26 MB（MainPipe） | Verilator 原始点数据库；每个构建一份，13 个构建合计 228 MB |
| `coverage-audit.json` | **260 MB** | 逐点审计：每个未覆盖 toggle 都带源码行，DCache 有 33 万 toggle 点 |
| 历史运行 × 5 | 每份 100–310 MB | 每次全量回归都留一份，之前累计了 5 份 |

降到现在 **84 MB** 的做法（`tools/compact_results.py`）：

1. 逐点 `coverage-audit.json` → `.json.gz`（260 MB → 3.9 MB）；
2. 保留 `coverage-audit-summary.json`（逐构建数字，13 KB）与 `coverage-audit.md`；
3. 删除原始 `coverage.dat`（仅用于重算审计；需要时重跑测试即可重建），
   LCOV `coverage.info` 保留为 `.gz`；
4. 只保留当前基线 + 被报告引用的历史运行，删除 99 个被取代的中间运行（97 MB）；
5. 13 个 Picker 构建目录里各有一份 28 MB 的 `xspcomm`，改为共享
   `dut/xspcomm-shared`（361 MB → 28 MB）。

工程总大小从 **1.2 GB → 约 600 MB**，其中 `dut/`（Picker 构建产物，跑测试必需）
约 490 MB、`results/` 约 40 MB、`rtl/` 17 MB。
